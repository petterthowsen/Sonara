# Godot Device Views

## Overview
- Device metadata exposes up to four view types (`Panel`, `Window`, `Companion`, `Compact`) registered via PackedScene references.
- All device visuals extend `DeviceView`, which binds to a `DeviceInstance` and supplies `_on_view_shown`/`_on_view_hidden` lifecycle hooks.
- Panels host views; they are not views. `DevicePanel` (`devices/device_lane/`, the full panel in DeviceLane and nested folders) hosts the Panel, Companion and Window views. `CompactDevicePanel` (`devices/compact/`, mixer lists) builds its own `CompactParameterControl`s and does not load a Compact view yet.
- View types: Panel = custom UI in the panel. Window = popup view for devices without a native GUI. Companion = replaces the Panel view while the Window view or native plugin GUI is open. Compact = reserved for `CompactDevicePanel`.

## Registration
- Built-in view scenes are preloaded in the `BUILTIN_*_SCENES` consts of `DeviceViewFactory.gd`. To give a built-in a view, add its device ID there; never store file-system paths.
- `DeviceViewFactory.register_builtin_views` is connected to `DeviceRegistry.device_registered`, so views are attached as each `/builtin/info` arrives, before any panel binds an instance.

## DeviceInstance Factory
- `DeviceViewFactory.create(instance, type)` (`devices/DeviceViewFactory.gd`) instantiates the registered PackedScene, asserts the node extends `DeviceView`, sets the `view_type`, and returns it; callers should treat `null` as "view unsupported".
- Device views implement `_on_bind()` to wire signals and use `_on_view_shown()`/`_on_view_hidden()` for data subscriptions to keep OSC listeners scoped to visibility.

## Drops and channel lookup
- Every device drop goes through `DeviceDropUtil`. Device drags carry a `DeviceDrag` payload (`DeviceDrag.start(self, inst)` in `_get_drag_data`); `DeviceDropUtil` unwraps it, so its functions also take a bare `DeviceInstance` or `Asset`.
- Rows of panels (DeviceLane, ChannelDeviceList, NestedDeviceList) expose a `drop_host: DeviceChainDropHost` (accept/drop rules and insert indices, no spacer nodes). DeviceLane and ChannelDeviceList are drop roots: `DeviceDropTarget.resolve(root, data, mouse)` picks the innermost row under the pointer and returns an INSERT between panels or ONTO a panel header (child into a container, file load). Panel and list drop handlers call `DeviceDropTarget.resolve_for(self, data)`, and the root's `_process` draws the `DropIndicator`. Controls that take device drops themselves (drum pads) join `DeviceDropTarget.OWN_DROPS_GROUP`. See `godot-drag-and-drop.md`.
- Drops are synchronous. A new instance that needs a file gets `DeviceInstance.queue_file_load(path)` before `DeviceAddCommand`; `Channel.add_device()` loads it right after the engine creates the device. Never `await` a timer before `load_file`.
- Find a device's channel with `DeviceInstance.get_channel()`, not `Sonara.editor.project.get_channel_by_id(inst.channel_id)`.

## Multi-out devices and drum pad lanes
- `data/AuxReturnSync.gd` owns the multi-out contract (spec: `docs/specs/001-multi-out-devices`). Every extra stereo output of a root device feeds a nested return channel with no timeline track. Drum Machine: one return per pad (`Channel.aux_pad_note`, bus = child order). Other devices: "Out N" returns in `DeviceInstance.return_channel_ids`. `Channel` hooks call it on add/remove/move; don't create or delete return channels anywhere else.
- A pad persists without a device. Removing the pad device (`DeviceRemoveCommand`) empties the pad and keeps its return. A device added on that note adopts the return. `ChannelDeleteCommand` on a pad return removes the pad; plugin returns can't be deleted on their own (`Channel.is_plugin_return()`).
- A pad return's device row is its pad lane (`devices/PadLane.gd`): [pad device][return devices…]. List devices with `PadLane.devices(channel)` and rebuild on `PadLaneWatcher.changed` while `active()`. `DeviceChainDropHost` already routes pad-lane drops through `PadLane.drop`, and positions there are lane indices. The front device is the Drum Machine child on the pad note; moves between the Drum Machine and the return channel use `DeviceTransferCommand`.

## Simple View (generated panels)
- Spec: `docs/specs/004-simple-view/`. Code in `devices/simple_view/`.
- Fallback rule: `DeviceViewFactory.create` returns `SimpleView` for a Panel view when `Device.uses_simple_view(params)` (not a container, at least one visible parameter per `ParamClassifier.is_visible`) and the device has no Panel view of its own, or has one but the DevicePanel "Simple" toggle is on (`Sonara.get_config("devices/simple_view/<id>")`).
- Pipeline: `DeviceKind.infer` → `ParamClassifier.classify` (with a strategy) → `CompoundDetector.detect` (xy, envelope, eq_band) → `SimpleLayoutGenerator.group_items` → `page_for_group` → `GridPacker.pack_pages`. Module paths group parameters when they're hierarchical or shared; otherwise `NameSections` groups by the sections names spell out (`Oscillator 1 Volume` → group "Oscillator 1", label "Volume"; `Filter Cutoff` → "Filter"; a numbered family with more than 8 instances or under 2 items each becomes one group with numbered labels, e.g. "Pitch 3"), but only when that covers at least half the items. Whatever is left goes to the strategy's role groups. Sections of one family stay adjacent in the importance order. Pages are categories: everything is on Main except groups whose strategy entry names a `page` (synth: Modulation, Effects). Pages are `rows` tall (4) and grow sideways up to `SimpleLayout.MAX_PAGE_COLUMNS` (24) before continuing on a new page. Each group gets a block (`GridPacker.group_block`): up to 4 one-row cells take a single row, otherwise the narrowest 2-row block up to 8 columns wide, otherwise full height. `GridPacker.Columns` places blocks in order, stacking them down a column (beside the previous one when the column is already wide enough) and starting a new column when one doesn't fit, so a page reads top to bottom, then left to right.
- Extension point: add a kind in `DeviceKind` and a `strategies/<Kind>Strategy.gd` extending `GenericStrategy` (role keywords, weights, groups, optional `page` per group), then map it in `SimpleLayoutGenerator.strategy_for`.
- Layouts: `SimpleLayoutStore` loads/saves `~/.config/sonara/device_layouts/<sanitized id>-<hash>.json` (`SimpleLayout`, version 1: `generator`, `grid.rows`, `pages[{title, groups, controls[{kind, params, rect, group?, label?, unit?}]}]`, `rect` = `[col, row, w, h]` cells; an envelope may carry `stages`, e.g. `"ads"`, and then binds one param per stage). A loaded layout is reconciled against the current parameters; a file that fails to parse is never overwritten. A never-edited (`generated`) layout whose `generator` is older than `SimpleLayoutGenerator.VERSION` is regenerated on load, so bump that constant when generation rules change. Footprints live in `SimpleControlKinds.FOOTPRINT`.
- Rendering: `SimpleControl` must stay inside its cell rect (it clips; inner controls need a small minimum size). A segmented control falls back to a dropdown when its labels don't fit. An enum whose labels are consecutive integers (`ParamClassifier.is_integer_enum`) gets a `spinbox` that counts in label values. Group titles get their own header strip in `SimpleView` pixel placement, drawn centered in `group_title_color` (white), with `group_margin` (2 px) kept clear around each box; control titles use the dimmer `SimpleControl.title_color`. Pixel placement also fills gaps without touching the saved grid: `SimpleView.fit_groups` grows each group box down, then right, until it meets another group, an ungrouped control or the page edge, and the group's controls are spread evenly over the grown box (equal gaps between and around columns and rows). A page narrower than the widest page is centered.
- Sizing: `SimpleView.cell_size` (76×68) sets how big controls are; knobs fill their cell. The grid is only as tall as the rows the page uses. The view's minimum width is the widest page's grid width (so switching pages doesn't shift neighbouring devices), so the DevicePanel widens to fit. The view never scrolls: its root is a VBoxContainer (page tabs above the grid) whose minimum size comes from its children, and pages split content that doesn't fit. Page tabs clip and scroll with arrows when they don't fit. Kinds are saved in the layout file, so a classifier change reaches an existing device only after its layout is regenerated (bump `SimpleLayoutGenerator.VERSION`, or delete the file).
- Headless tests: `tests/test_simple_layout_model.gd`, `tests/test_simple_layout_generator.gd`. Code loaded by tests can't reference autoloads like `Sonara` by name; look them up through the scene tree.

## Parameter Typing
- `DeviceParameter.param_type` is one of `"float"`, `"bool"`, or `"enum"`; `"enum"` parameters must populate `enum_values` with display strings where the index matches the engine payload.
- Keep `default_value`, `min_value`, and `max_value` aligned with the declared type: booleans stay in `[0,1]`, enums use integer indices, floats can still mark `is_logarithmic`.
- Skip OSC writes for UI-only fields by setting `syncable = false`; `DeviceInstance.sync_parameter_to_engine()` respects the flag.
- UI controls (e.g., `CompactParameterControl`) branch on `param_type` to choose a checkbox, option button, or slider—make sure new views follow the same pattern when rendering device parameters.

## DevicePanel Orchestration
- The Parameters tab starts closed: the View is what a device normally shows. `_apply_default_tab` opens Parameters only for a device with no view, and closes them again if a view arrives later (plugin parameters advertised after binding), unless the user picked a tab.
- Binding a device loads the Panel view first; the View pane (toggled by the left header's View button) hides when neither a Panel nor a Companion view is loaded. Parameters/CCs/File are one ButtonGroup with `allow_unpress`; the header's FoldoutToggle opens the container children folder.
- The Window toggle is visible only when `device.has_gui()` or `has_window_view()` is true; pressing it either opens the plugin's native GUI or spawns a `Window` under `Sonara.editor` containing the Window view.
- `_apply_window_state()` shows the Companion view in the View pane instead of the Panel view whenever the device window (Window view or native plugin GUI) is open and the device advertises one; closing the window frees the view and returns to the Panel.
- Container children: `DevicePanel` adds a `ContainerFolder` (slide-out pane at the end of `Content/HBox`) that wraps a `NestedDeviceList`, which instantiates one `DevicePanel` per child (recursive). The FoldoutToggle only shows for `is_container()` devices. When `container_focuses_one_child()` (Layer, Drum Machine) the folder shows a single child; a custom view picks it by emitting `DeviceView.container_child_requested`, and gets `set_focused_child()` back. Drops onto a container reveal the new child (`after_drop_onto`).
- Scene layout (`DevicePanel.tscn`): `VBox/TopHeader` (light, name, FoldoutToggle; `header`, the drop-onto rect), `VBox/HBox/LeftHeader/TabButtons` (View, Window, Parameters, File; CCs button duplicated at runtime), `VBox/HBox/Content/HBox` (Parameters, CCs, File, View, ContentFolder).
- Views are bound before being added to the scene tree, and every show/hide path calls `_on_view_shown()` or `_on_view_hidden()` so long-running subscriptions clean up reliably.
